# Why go.uber.org/mock (gomock) — Unit Testing the Store Layer

## The decision

Business logic that sits on top of the database — most notably `transferTx` in [db/store/store_transaction.go](../db/store/store_transaction.go) — is unit tested against a generated mock of the `sqlc.Querier` interface, using [go.uber.org/mock](https://github.com/uber-go/mock) (the actively maintained successor to `golang/mock`), rather than only against a real Postgres instance.

## Why not the alternatives

**Why not test only against a real database.** This codebase *also* has real-database integration tests (see [db/sqlc/main_test.go](../db/sqlc/main_test.go), [db/store/main_test.go](../db/store/main_test.go), [db/store/store_transaction_integration_test.go](../db/store/store_transaction_integration_test.go)), and those matter — they're the only way to catch things a mock can't, like an actual constraint violation or the real behavior of `SELECT ... FOR UPDATE` under concurrency. But they require a running Postgres, they're slower, and — critically for `transferTx` specifically — some of the scenarios that matter most are hard or slow to provoke for real: "the second `IncrementAccountBalance` call fails," "accounts are locked in ascending-ID order regardless of which one is `from`," "nothing after `CreateTransfer` runs if it errors." A mock lets you assert exactly that shape of failure or exactly that call order, deterministically, in milliseconds. The two approaches aren't competing — they check different things.

**Why not hand-written fakes.** A hand-written fake implementing `Querier` (a struct with a field per method, or an in-memory map standing in for the accounts table) is a legitimate alternative, and for a small interface it can be less machinery than a code generator. It stops paying off here because `Querier` has one method per SQL query — every table, every query variant — and grows every time a query is added (see [SQLC_SETUP.md](SQLC_SETUP.md)); hand-maintaining a fake that implements all of it, correctly, in step with sqlc regeneration, is exactly the kind of repetitive-and-therefore-error-prone work a generator exists to remove. It also can't give you call-order assertions (`gomock.InOrder`) or "this must be called exactly N times" (`.Times(0)`) without you building that machinery yourself.

**Why gomock specifically, and not testify's `mock` package.** Both generate/provide a mock satisfying an interface; the meaningful difference is *how* expectations are declared. testify's `mock.Mock` is typically hand-embedded per fake and matches calls by string method name at runtime — a typo in `.On("CreateTranfer", ...)` compiles fine and fails at test-run time with a confusing "unexpected call" error. gomock is code-generated per interface (`MockQuerier` has an actual `CreateTransfer` method), so `q.EXPECT().CreateTransfer(...)` is a real, compiler-checked method call — rename or change the signature of a `Querier` method and every stale expectation is a compile error, not a runtime surprise. Given that `Querier` is machine-generated from SQL and changes shape whenever a query changes, keeping its mock equally machine-generated (and equally type-checked) is the consistent choice.

**The trade-off you're accepting.** A mock only proves that `transferTx` calls `Querier` the way you told the mock to expect — it says nothing about whether those calls, run against real Postgres, actually behave that way (a mocked `GetAccountByIdForUpdate` doesn't actually take a row lock). That's exactly why this project keeps the integration test suite alongside the mock-based one instead of replacing it.

## How it's wired in this codebase

```
db/sqlc/querier.go     <- sqlc-generated interface (emit_interface: true)
        │
        │  mockgen
        ▼
db/mock/querier.go      <- generated: MockQuerier implementing Querier
```

Three mechanics worth understanding:

1. **The mock is generated from the interface, not written by hand.** [db/mock/querier.go](../db/mock/querier.go) carries the same `// Code generated ... DO NOT EDIT.` header as sqlc's own output, generated by `make generate-mock` (see the Makefile), which runs:
   ```
   go run go.uber.org/mock/mockgen@latest -package mockdb -destination db/mock/querier.go github.com/DewaSRY/core-service/db/sqlc Querier
   ```
   Any time `Querier` gains, loses, or changes a method — which happens every time a query is added via sqlc (see [SQLC_SETUP.md](SQLC_SETUP.md)) — this needs to be re-run. There's no drift-detection test enforcing that today, so treat "ran `make sqlc`" and "ran `make generate-mock`" as a single step, not two independent ones you might forget the second half of.

2. **`gomock.NewController(t)` ties expectations to the test's lifetime and fails it automatically.** Every test constructs `ctrl := gomock.NewController(t)` and `q := mockdb.NewMockQuerier(ctrl)`. Passing `t` means the controller registers a cleanup on the test itself — it doesn't need an explicit `defer ctrl.Finish()` in modern gomock — and any `EXPECT()` that was set up but never called (or called more times than expected) fails that specific subtest, not the whole suite. This is what makes an assertion like `q.EXPECT().CreateTransfer(...).Times(0)` in [db/store/store_transaction_test.go](../db/store/store_transaction_test.go) meaningful: it's not just "don't return an error," it's "this must never be called," enforced by the framework rather than by manually checking a counter.

3. **`gomock.Any()` vs. an exact value is a real design choice per argument, not a default.** Every `EXPECT()` call in this codebase matches `ctx` with `gomock.Any()` (the context is plumbing, not something worth asserting on) but matches business parameters exactly — `q.EXPECT().CreateTransfer(gomock.Any(), arg)` asserts the *exact* `CreateTransferParams` the code under test is expected to build. That's a deliberate strictness: if `transferTx` ever passed the wrong `FromAccountID` into `CreateTransfer`, this fails immediately with a clear "no matching call" error, rather than the test only checking the returned `TransferTxResult` and missing that the *input* to the database was wrong.

4. **`gomock.InOrder` encodes the sequence itself as a testable property.** `transferTx` has to lock the lower account ID first, create the transfer, then debit, then credit — get any of that order wrong and you reintroduce the deadlock risk the whole design exists to avoid. `gomock.InOrder(q.EXPECT()..., q.EXPECT()..., ...)` (see `lockAccounts` and the main success case in [store_transaction_test.go](../db/store/store_transaction_test.go)) asserts that exact call sequence, not just that all the calls eventually happened — a regression that reorders two steps fails this test even though each individual call still matches its expectation.

## Day-to-day integration

**Writing a new mock-based test:**

```go
ctrl := gomock.NewController(t)
q := mockdb.NewMockQuerier(ctrl)

q.EXPECT().
    GetAccountById(gomock.Any(), int64(1)).
    Return(sqlc.Account{ID: 1, Owner: "dewa", Balance: "1000", Currency: "USD"}, nil)

result, err := yourFunctionUnderTest(context.Background(), q, ...)
// assert on result/err
```

- Depend on `sqlc.Querier` (the interface), never `*sqlc.Queries`, in any function you want to be able to test this way — that's the whole precondition for mockability, and it's why `transferTx` takes a `sqlc.Querier` parameter instead of reaching for `store.Queries` directly (see [db/store/store_transaction.go](../db/store/store_transaction.go)).
- Use `.Times(0)` to assert a call *must not* happen — this is how [store_transaction_test.go](../db/store/store_transaction_test.go) proves that an early validation failure (same account, non-positive amount) short-circuits before touching the database at all.
- Use `gomock.InOrder(...)` whenever call sequence is part of the correctness contract, not just call presence.
- Return a Go `error` (`errors.New("...")`, or a sentinel like `sql.ErrNoRows`) from an `EXPECT().Return(...)` to test the failure path of each individual step — this is how the test suite covers "what if `CreateTransfer` fails," "what if the second `IncrementAccountBalance` fails," etc., without ever needing a real database in a broken state.

**Regenerating after a schema/query change:** run `make sqlc` then `make generate-mock`, in that order — the mock is generated *from* the sqlc-generated interface, so it's always the second step.

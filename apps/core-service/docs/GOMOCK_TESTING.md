# Gomock Unit Testing — As Implemented

## Who this doc is for

You're comfortable with Go's `testing` package and table-driven tests; you
don't need to have used `go.uber.org/mock` (gomock) before — Section 0 covers
the parts of its API that aren't obvious from the method names.

This doc is verified against source, not aspirational: every claim below cites
a `file:line` you can open and check. Read it closely before building on top
of it — in particular, don't assume `internal/db/store`'s `*Tx` business logic
(`transferTx`, `deleteAccountTx`, `createAccountTx`, `depositTx`) has dedicated
mock-based unit tests today. It doesn't (Section 3), and that's the single
biggest gap this doc needs you to know about going in.

## Section 0 — Background Primer: why gomock, not the alternatives

| Approach | What it tests against | Compiler-checked expectations? | Call-order / call-count assertions? | Cost to maintain as `Storer` grows |
|---|---|---|---|---|
| Real Postgres integration test | An actual running database | N/A | Only by provoking real timing/locking | Low per-test, but slow and can't force some failure shapes deterministically |
| Hand-written fake (`struct` implementing `Storer`) | A struct you wrote by hand | Yes (real Go methods) | Only if you build it yourself | Grows every time `Storer` gains a method — one per SQL query (see [SQLC_SETUP.md](SQLC_SETUP.md)) |
| testify `mock.Mock` | A hand-embedded `mock.Mock`, matched by string method name | No — `.On("CreateTranfer", ...)` typos compile fine, fail at run time | Built-in via `.Once()`/ordering helpers, less ergonomic | Low boilerplate per mock, but no compile-time safety net |
| **gomock (`go.uber.org/mock`)** | A generated mock (`MockStorer`), one real method per interface method | **Yes** — `q.EXPECT().CreateTransfer(...)` is a real, type-checked call | Yes — `gomock.InOrder`, `.Times(n)` | Regenerated by a single Makefile target whenever the interface changes |

The project mocks `Storer` (`internal/db/store/store.go:13-19`) — not the raw
sqlc `Querier` directly — with `go.uber.org/mock/mockgen`, producing
`internal/db/mock/querier.go`'s `MockStorer`. `Storer` is machine-generated in
part (it embeds `db.Querier`, which sqlc regenerates on every query change) and
hand-written in part (the four `*Tx` methods), so keeping its mock equally
machine-generated — and equally compiler-checked — is the consistent choice:
rename a `Storer` method and every stale `EXPECT()` becomes a compile error,
not a confusing runtime "unexpected call."

**Gotchas that surprise newcomers to gomock:**

1. **The mock is generated from `Storer`, not from `sqlc.Querier`.** If you go
   looking for a `MockQuerier`, you won't find one — `MockStorer` is the only
   generated mock in this repo, and it includes both the embedded `Querier`
   methods and the four `*Tx` methods (see Section 1).
2. **No `defer ctrl.Finish()` anywhere.** Every test passes `t` straight into
   `gomock.NewController(t)`, which registers its own `t.Cleanup` — an
   `EXPECT()` that's set up but never called fails that subtest automatically,
   with no explicit teardown call needed (confirmed: `grep -rn "ctrl.Finish"`
   across this repo returns zero hits).
3. **`gomock.Any()` vs. an exact value is a per-argument design choice, not a
   default.** Every `EXPECT()` in this codebase matches `ctx` with
   `gomock.Any()` but matches business parameters exactly (or via
   `DoAndReturn`'s callback, which lets a test assert on individual fields of
   an argument struct rather than requiring bit-for-bit equality) — see
   Section 2 for why that distinction matters here specifically.

## Section 1 — Architecture at a Glance

The composition root for the mock itself is a single Makefile target, not a
`//go:generate` directive in the source (`grep -rn "^//go:generate"` across
the repo returns nothing):

```makefile
# Makefile:36-37
generate-mock: 
	go run go.uber.org/mock/mockgen@latest -package mockdb -destination internal/db/mock/querier.go github.com/DewaSRY/core-service/internal/db/store Storer
```

That target doesn't implement any test logic itself — it delegates entirely to
`mockgen`, pointed at the `Storer` interface.

| Concern | Owner (file) | Analogy |
|---|---|---|
| Generated query methods | `internal/db/sqlc/querier.go` (`Querier`, sqlc `emit_interface: true`) | The raw API surface a real database exposes |
| Business-logic contract | `internal/db/store/store.go:13-19` (`Storer` — embeds `db.Querier` + 4 `*Tx` methods) | The full contract a `Handler` is allowed to depend on |
| Generated stand-in | `internal/db/mock/querier.go` (`MockStorer`, via `mockgen`) | A stunt double that stands in for the whole contract, scripted call-by-call |
| Script for the stand-in | Each test's `buildStubs`/`tc.buildStubs` closures | The stunt double's shot list — what it's told to do and return |
| The scene itself | `internal/api/<domain>/*_handler_test.go`'s `newTestRouter` + `httptest` | The take — a real HTTP request run against real Gin routing and real middleware, with only the database swapped for the stand-in |

Why split it this way: `Handler` structs hold a `store.Storer` field, never a
concrete `*_store`, specifically so tests can substitute `MockStorer` without
a database. The consequence worth flagging now, and explained fully in
Section 3: because every `Handler` mocks `Storer` at the *whole-method*
granularity (`TransferTx` as one call, not its internal steps), a handler test
can prove "the handler called `TransferTx` with the right arguments and
handled its result," but it structurally cannot prove `TransferTx`'s own
internals — lock order, decimal math, short-circuit validation — are correct.

## Section 2 — Handler Tests: the layer that actually uses `MockStorer`

**The problem this solves.** A `Handler` (`internal/api/account`,
`internal/api/auth`, `internal/api/transfer`) needs its full bind → call
`Storer` → map error → respond pipeline exercised through real HTTP semantics
(binding errors, status codes, JSON body shape) without a database.

**How it's actually implemented.** All three domain test files —
`internal/api/account/account_handler_test.go`,
`internal/api/auth/auth_handler_test.go`,
`internal/api/transfer/transfer_handler_test.go` — follow the identical shape:

1. A `newTestRouter` helper builds a bare `gin.New()` engine and wires only
   the middleware relevant to the domain under test, then constructs the
   `Handler` with a `store.Storer` passed in (which the caller fills with
   `mockdb.NewMockStorer(ctrl)`):

   ```go
   // internal/api/account/account_handler_test.go:41-57
   func newTestRouter(t *testing.T, storer store.Storer) (*gin.Engine, token.Maker) {
       gin.SetMode(gin.TestMode)
       tokenMaker, err := token.NewJWTMaker(testSecretKey)
       require.NoError(t, err)

       router := gin.New()
       router.Use(core.ErrorHandlerMiddleware(slog.New(slog.NewTextHandler(io.Discard, nil))))

       authorized := router.Group("/api/v1")
       authorized.Use(core.AuthMiddleware(tokenMaker))

       h := &Handler{Store: storer}
       h.RegisterRoutes(authorized)

       return router, tokenMaker
   }
   ```

   `internal/api/transfer/transfer_handler_test.go:48-64` is byte-for-byte the
   same pattern. `internal/api/auth/auth_handler_test.go:44-60` differs only
   because `auth` has both public and authorized routes — it registers
   `RegisterPublicRoutes` on the base `v1` group, then nests an `authorized`
   sub-group behind `core.AuthMiddleware` for `RegisterAuthorizedRoutes`.

2. Small per-file helpers build requests: `authHeaderFor(t, tokenMaker,
   userID)` (`internal/api/account/account_handler_test.go:59-63`,
   identical in `transfer`) mints a real JWT via `token.NewJWTMaker`, and
   `doAuthenticatedRequest(t, router, method, path, body, authHeader)`
   (`internal/api/account/account_handler_test.go:65-84`) marshals the body,
   sets headers, and drives the request through `router.ServeHTTP` via
   `httptest`. `auth`'s equivalents are split one-per-endpoint
   (`doRegisterRequest`, `doLoginRequest`, `doGetProfileRequest`) since only
   `/auth/profile` needs an `Authorization` header.

3. Each `Test*` function is table-driven: a slice of cases, each with a
   `buildStubs` closure that sets `MockStorer` expectations and a
   `checkResponse` closure that asserts on the recorded response, run through
   an identical `t.Run` loop that constructs a *fresh* `gomock.NewController`
   and `MockStorer` per case:

   ```go
   // internal/api/account/account_handler_test.go:122-132
   for _, tc := range testCases {
       t.Run(tc.name, func(t *testing.T) {
           ctrl := gomock.NewController(t)
           q := mockdb.NewMockStorer(ctrl)
           tc.buildStubs(t, q)

           router, tokenMaker := newTestRouter(t, q)
           recorder := doAuthenticatedRequest(t, router, http.MethodPost, "/api/v1/accounts", tc.body, authHeaderFor(t, tokenMaker, testUserID))
           tc.checkResponse(t, recorder)
       })
   }
   ```

| Domain file | Table-driven tests it defines |
|---|---|
| `internal/api/account/account_handler_test.go` | `TestCreateAccount`, `TestUpdateAccount`, `TestDetailAccount`, `TestListmeAccounts`, `TestSearchAccountByNumber`, `TestDeleteAccount` |
| `internal/api/auth/auth_handler_test.go` | `TestRegisterUser`, `TestLoginUser`, `TestGetProfile` |
| `internal/api/transfer/transfer_handler_test.go` | `TestDeposit`, `TestListAccountEntriesByAccountId`, `TestListRecentTransferDestinations`, `TestListAccountTransactionHistory`, `TestTransactionTransfer` |

**`gomock.Any()` vs. exact match, in practice.** Two styles show up side by
side, and which one a case uses says something about what that case is
proving:

```go
// internal/api/account/account_handler_test.go:96-104 — exact struct fields,
// asserted from inside a DoAndReturn callback (business-parameter checking)
q.EXPECT().CreateAccountTx(gomock.Any(), gomock.Any()).DoAndReturn(
    func(_ context.Context, arg store.CreateAccountTxParams) (db.Account, error) {
        require.Equal(t, testUserID, arg.UserID.Int64)
        require.Equal(t, "Savings", arg.Name)
        require.False(t, arg.IsMain)
        return db.Account{ID: 2, Balance: "0", Currency: "IDR", ...}, nil
    },
)
```

```go
// internal/api/account/account_handler_test.go:151-157 — a fully exact
// expected value, no gomock.Any() on the params struct at all
q.EXPECT().UpdateAccount(gomock.Any(), db.UpdateAccountParams{
    ID:          existingAccount.ID,
    Name:        sql.NullString{String: "New Name", Valid: true},
    Description: sql.NullString{String: "new description", Valid: true},
}).Return(db.Account{ID: existingAccount.ID, Name: sql.NullString{String: "New Name", Valid: true}}, nil)
```

`ctx` is always `gomock.Any()` everywhere in the repo — it's plumbing, never
worth asserting on.

**`.Times(0)` as a short-circuit proof.** Every domain file uses `.Times(0)`
to prove a validation failure stops the handler *before* it ever reaches the
store — not just "returned the right status code," but "never touched the
database":

```go
// internal/api/account/account_handler_test.go:113-115 (missing required name)
q.EXPECT().CreateAccountTx(gomock.Any(), gomock.Any()).Times(0)
```

```go
// internal/api/transfer/transfer_handler_test.go:128-129 (non-positive amount)
q.EXPECT().GetAccountById(gomock.Any(), gomock.Any()).Times(0)
q.EXPECT().DepositTx(gomock.Any(), gomock.Any()).Times(0)
```

```go
// internal/api/auth/auth_handler_test.go:130-134 (password mismatch — proves
// none of the three downstream calls happen, not just the first one)
q.EXPECT().GetUserByEmail(gomock.Any(), gomock.Any()).Times(0)
q.EXPECT().CheckIsUsernameExist(gomock.Any(), gomock.Any()).Times(0)
q.EXPECT().CreateUser(gomock.Any(), gomock.Any()).Times(0)
```

**Rough edge — no `gomock.InOrder` anywhere in this repo.** `gomock.InOrder`
would assert that a sequence of calls happens in a specific order (useful for
proving lock-then-write ordering); a repo-wide `grep -rn "InOrder"` returns
zero matches. Multiple sequential `EXPECT()` calls in these files (e.g. the
three-step deposit flow, or auth's `GetUserByEmail` →
`CheckIsUsernameExist` → `CreateUser` chain) read like an ordered sequence but
are matched by gomock in any order by default — a handler that called them out
of sequence would still pass these tests.

**Divergence from the doc comment.** `account`'s and `transfer`'s
`newTestRouter` carry a comment claiming they wire things "exactly as
`NewServer` wires the... group in production"
(`internal/api/account/account_handler_test.go:38-40`,
`internal/api/transfer/transfer_handler_test.go:45-47`). That's only true for
the `AuthMiddleware`-on-the-authorized-group piece — see the cross-feature
coupling section below for the full gap against production's middleware
chain.

## Section 3 — Deliberately Missing: `*Tx` Business-Logic Unit Tests

**The problem this would solve, if it existed.** `transferTx`,
`deleteAccountTx`, `createAccountTx`, and `depositTx`
(`internal/db/store/store_transaction.go`, `store_account.go`,
`store_account_create_tx.go`, `store_account_deposit_tx.go`) are parameterized
on `sqlc.Querier` — not the concrete `*sqlc.Queries` — specifically so they
*can* be unit tested against a mocked `Querier`, independent of the handler
layer, to assert things like "accounts are locked in ascending-ID order
regardless of which one is `from`" or "nothing after `CreateTransfer` runs if
it errors."

**What actually exists today: nothing.** `internal/db/store` has zero
`*_test.go` files (`find internal/db/store -name "*_test.go"` returns
nothing). This isn't an oversight this doc is catching for the first time —
it's already called out in [AGENTS.md](../AGENTS.md)'s "Doc drift" section as
having been removed in a "update store codebase" commit, alongside the
now-nonexistent `store_transaction_test.go`, `main_test.go`, and
`store_transaction_integration_test.go` files an earlier version of this doc
described in detail.

**The actual end-to-end consequence today:** the only coverage `transferTx`
(and its siblings) get is *indirect*, through
`internal/api/transfer/transfer_handler_test.go`, which mocks the entire
`Storer.TransferTx` call as one opaque unit:

```go
// internal/api/transfer/transfer_handler_test.go:445-452
q.EXPECT().TransferTx(gomock.Any(), gomock.Any()).DoAndReturn(
    func(_ context.Context, arg db.CreateTransferParams) (store.TransferTxResult, error) {
        require.Equal(t, fromAccountID, arg.FromAccountID)
        require.Equal(t, toAccountID, arg.ToAccountID)
        require.Equal(t, "25.00", arg.Amount)
        return store.TransferTxResult{FromEntry: db.Entry{ID: 11}}, nil
    },
)
```

That proves the *handler* passed the right arguments into `TransferTx` and
handled its return value correctly. It cannot catch a regression *inside*
`transferTx` itself — a swapped lock order, a skipped currency check, a wrong
call sequence — because the mock never runs `transferTx`'s real body at all.

If you touch `transferTx`/`deleteAccountTx`/`createAccountTx`/`depositTx`,
don't assume the handler test suite protects you. The pattern to reach for —
a mocked `sqlc.Querier` passed directly into the private `fooTx(ctx, q
sqlc.Querier, arg)` function, asserting call order with `gomock.InOrder` —
still applies conceptually even though no file implementing it exists in this
repo right now.

## Section 4 — The Other Kind of Test: Real Postgres, No Mocking At All

**The problem this solves.** Some behavior can't be verified against a mock
because the mock doesn't have it — an actual DB-level check constraint firing,
or `SELECT ... FOR UPDATE`'s real locking semantics. `internal/db/sqlc/*_test.go`
covers this by running against a real, disposable Postgres transaction:

```go
// internal/db/sqlc/main_test.go:1-50 (package db, i.e. internal/db/sqlc)
var testDB *sql.DB
var dbSource = "postgresql://simple_bank:password@localhost:5433/simple_bank?sslmode=disable"

func TestMain(m *testing.M) {
    con, err := sql.Open(dbDriver, dbSource)
    ...
    testDB = con
    os.Exit(m.Run())
}

func createTestQueries(t *testing.T) *Queries {
    tx, err := testDB.Begin()
    require.NoError(t, err)
    t.Cleanup(func() {
        tx.Rollback()
    })
    return New(tx)
}
```

Every test in `account_test.go`, `entries_test.go`, `transfers_test.go` calls
`createTestQueries(t)` and gets a `*Queries` backed by its own transaction,
rolled back automatically in `t.Cleanup` — so tests never pollute each other
or the shared local database, and need no manual fixture teardown.

**Rough edge worth flagging:** this integration layer tests bare sqlc-generated
queries only. It does **not** cover `internal/db/store`'s `*Tx` wrappers —
`internal/db/store` has no integration tests any more than it has mock-based
unit tests (Section 3). A bug that only manifests when a `*Tx` function's
multi-step logic runs against real Postgres (e.g. a real deadlock from a
wrong lock order) has no test layer that would currently catch it.

## Section 5 — Small Helpers, No Business Logic

A few helper functions exist purely to remove request/response boilerplate
from test bodies — worth knowing about so they don't get mistaken for part of
the system under test:

- `itoa(id int64) string` (`internal/api/account/account_handler_test.go:34-36`,
  identically in `transfer_handler_test.go:35-37`) — formats an account ID
  into a URL path segment.
- `mustDecimal(t *testing.T, s string) decimal.Decimal`
  (`internal/api/transfer/transfer_handler_test.go:39-43`) — parses a decimal
  string and fails the test on error, so test bodies can write amounts as
  plain string literals.
- `doAuthenticatedRequest` / `doRegisterRequest` / `doLoginRequest` /
  `doGetProfileRequest` — pure HTTP plumbing (marshal body, set headers, drive
  `router.ServeHTTP`, return the recorder). None of these assert anything;
  assertions live entirely in each test case's own `checkResponse`.

## Cross-Feature Coupling: Middleware Tests Don't Use Mocks, but Handler Tests Depend on Them Being Right

`internal/api/core`'s own middleware tests
(`internal/api/core/logging_middleware_test.go`,
`internal/api/core/auth_middleware_test.go`) use no gomock at all — no
`Storer`, no `MockStorer` — because they're testing HTTP-layer concerns in
isolation. But every domain handler test *imports and runs* `core.AuthMiddleware`
and `core.ErrorHandlerMiddleware` for real (Section 2) — a regression in
either middleware would silently break handler tests across all three domains
without those tests' `buildStubs`/`checkResponse` closures ever hinting why.

**Worth flagging: handler tests don't replicate the production middleware
stack.** Production (`internal/api/server.go:69-73`) registers five
middleware in a load-bearing order:

```go
// internal/api/server.go:69-73
router.Use(core.RequestIDMiddleware())
router.Use(core.LoggingMiddleware(log, cfg))
router.Use(corsMiddleware(cfg.CORSAllowedOrigins))
router.Use(core.ErrorHandlerMiddleware(log))
router.Use(core.RecoveryMiddleware(log))
```

All three domain handler test files attach only two:
`core.ErrorHandlerMiddleware` globally and `core.AuthMiddleware` on the
authorized group (Section 2). They never exercise `RequestIDMiddleware`,
`LoggingMiddleware`, `corsMiddleware`, or `RecoveryMiddleware` — so a handler
test proves nothing about request-ID propagation, access logging, CORS
behavior, or panic recovery for that domain's endpoints.

The one place that *does* replicate the full production ordering is
`internal/api/core/logging_middleware_test.go:28-34`:

```go
// internal/api/core/logging_middleware_test.go:28-34
func newTestRouterWithConfig(log *slog.Logger, cfg config.Config) *gin.Engine {
    gin.SetMode(gin.TestMode)
    router := gin.New()
    router.Use(RequestIDMiddleware())
    router.Use(LoggingMiddleware(log, cfg))
    router.Use(ErrorHandlerMiddleware(log))
    router.Use(RecoveryMiddleware(log))
    return router
}
```

— with an explicit comment (`internal/api/core/logging_middleware_test.go:20-23`)
that this exists specifically so a regression in *ordering* (a panic
"recovered" into an empty 200 instead of a rendered 500) gets caught, even
though `NewServer` itself is never invoked in a test. This file omits only
`corsMiddleware`, which has no interaction with the error/recovery ordering
it's protecting. It uses no `Storer`/`MockStorer` — panics and error
propagation don't depend on the database layer at all.

## Summary: The Full Generation-to-Assertion Data Flow

```
internal/db/query/*.sql
        │  sqlc generate  (sqlc.yaml: emit_interface: true)
        ▼
internal/db/sqlc/querier.go        Querier interface (generated)
        │  embedded by
        ▼
internal/db/store/store.go         Storer interface = Querier + 4 hand-written *Tx methods
        │  mockgen (make generate-mock)
        ▼
internal/db/mock/querier.go        MockStorer (generated, implements Storer)
        │  constructed per test case
        ▼
mockdb.NewMockStorer(ctrl)  →  tc.buildStubs(t, q) sets EXPECT()/Return()/DoAndReturn()/Times(0)
        │  injected into
        ▼
Handler{Store: q}  →  RegisterRoutes(group)  on a gin.New() router with a subset of production middleware
        │  driven by
        ▼
httptest.NewRequest + router.ServeHTTP  →  httptest.ResponseRecorder
        │
        ▼
tc.checkResponse(t, recorder)   asserts status code / JSON body
```

Regenerating after a schema or query change is two Makefile steps, always in
this order (nothing enforces the ordering today — treat it as one step, not
two independently-rememberable ones):

```bash
make sqlc            # sqlc generate — regenerates internal/db/sqlc/querier.go
make generate-mock   # mockgen against the now-changed Storer interface
```

## Reference Table: Commands That Touch This Testing Layer

| Command | What it runs | Needs a database? |
|---|---|---|
| `make test` | `db-up` then `go test -v ./...` — everything, mock-based and Postgres-integration | Yes (via `db-up` dependency) |
| `make test-failed` | Full suite, greps output for `--- FAIL`/`FAIL` lines only | Yes |
| `make test-coverage` | `go test -v -coverprofile=coverage.out -covermode=atomic ./internal/api/...` — **handler/gomock tests only**, not `internal/db/store` or `internal/db/sqlc` | No |
| `make sqlc` | `sqlc generate` — regenerates `internal/db/sqlc/querier.go` from `internal/db/query/*.sql` | No |
| `make generate-mock` | `mockgen` against `internal/db/store.Storer`, regenerates `internal/db/mock/querier.go` | No |
| `make db-up` | Starts Postgres via docker-compose, runs migrations — the precondition `internal/db/sqlc/*_test.go` needs | Starts one |
| `go test ./internal/api/...` | Just the gomock-based handler tests, for one domain or all three | No |
| `go test ./internal/db/sqlc/...` | Just the real-Postgres integration tests | Yes |
| `go test ./internal/db/store/...` | Currently a no-op — no test files exist in this package (Section 3) | N/A |

`Makefile:92`'s `.PHONY` line also lists a `test-router-coverage` target that
doesn't exist anywhere else in the Makefile — a stale entry, not a command you
can actually run.

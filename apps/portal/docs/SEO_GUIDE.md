# SEO Guide — Current State & Implementation Playbook

## Who this doc is for

Anyone adding a new route or fixing metadata in `apps/portal`. Assumes
familiarity with the App Router basics from the root [AGENTS.md](../AGENTS.md)
(feature/page split, `proxy.ts`, `i18n/settings.ts`) but not necessarily with
Next.js's Metadata APIs. This is an **audit + playbook**, not a "how it's
already built" doc like the other files in this folder — most of what's
described in Section 3 doesn't exist yet. Every "current state" claim is
verified against source as of 2026-09-19, Next.js `16.3.3` (see
`package.json`). Note: this app's `middleware.ts` equivalent is `proxy.ts`
(a rename in this Next.js version — see the root `AGENTS.md` preamble); the
file-convention names referenced below (`app/robots.ts`, `app/sitemap.ts`,
`generateMetadata`) are unchanged from the Next.js you already know.

## 1. Where SEO Surfaces Live in This App

| Concern | Owner (file) | Notes |

| `<html lang>` | `app/[locale]/layout.tsx:50` | Set correctly today, per-locale |
| Locale URL prefixing + auth redirects | `proxy.ts` | Every path is force-redirected to `/{locale}/...`; no content negotiation |
| Crawl directives | `app/robots.ts` (file convention) | **Does not exist yet** |
| Sitemap | `app/sitemap.ts` (file convention) | **Does not exist yet** |
| PWA manifest | `app/manifest.ts:1-26` | Exists, but this is app-install metadata, not page SEO |
| Locale list/default | `i18n/settings.ts:1-2` | `["en", "id"]`, default `"en"` |

Route surface, for reference (actual folder names — the root `AGENTS.md`'s
`(public)`/`(protected)` names are stale; the real groups are `(auth)`,
`(protected)`, `(splash)`):

| Route | Group | Should be indexable? |
|---|---|---|
| `/` (landing) | `(auth)` | Yes |
| `/login`, `/register` | `(auth)` | Yes |
| `/dashboard`, `/account/[id]` | `(protected)` | **No** — session-gated content |
| `/auth-success`, `/logout` | `(splash)` | **No** — transient redirect-through pages |

Net effect: the only page a search engine can currently form a decent
snippet for is the landing page, in one language's worth of metadata
inheritance, with no way to discover any other URL (no sitemap) and no
signal to stay out of authenticated-only pages beyond the redirect.

## 3. Implementation Playbook

### 3.1 Fix root metadata + add `metadataBase`

`app/[locale]/layout.tsx:27-30` ships the `create-next-app` placeholder to
every route that doesn't override it (title/description merge rules: see
the "Merging"/"Inheriting fields" behavior in Next's own
[`generateMetadata` reference](../node_modules/next/dist/docs/01-app/03-api-reference/04-functions/generate-metadata.md#merging)).
Replace it with a real default and a `title.template`, and add
`metadataBase` so every relative URL used in `openGraph`/`alternates`
resolves to an absolute one instead of erroring at build time:

```ts
// app/[locale]/layout.tsx
export const metadata: Metadata = {
  metadataBase: new URL(process.env.NEXT_PUBLIC_SITE_URL ?? "http://localhost:3000"),
  title: {
    default: "Simple Bank",
    template: "%s | Simple Bank",
  },
  description: "Ledger-based core banking demo — accounts, deposits, and transfers.",
};
```

`NEXT_PUBLIC_SITE_URL` doesn't exist today — the only public env var
documented in `AGENTS.md`'s Configuration section is `NEXT_PUBLIC_API_URL`
(the backend). This is a new, separate public var (the portal's own
canonical origin, not the API's) — add it to `.env.local` and note it in
`AGENTS.md`'s Configuration section when you land this.

### 3.2 Add a shared SEO helper module

Alternates, canonical URLs, and default Open Graph fields will be needed by
every page that defines metadata (Section 3.3, 3.4). Following this repo's
own convention that a cross-cutting concern used by every feature belongs
in `lib/`, not duplicated per page (see AGENTS.md's "How the Code Is
Organized"), add `lib/seo/metadata.ts`:

```ts
// lib/seo/metadata.ts
import { locales, type AppLocale } from "@/i18n/settings";

const SITE_URL = process.env.NEXT_PUBLIC_SITE_URL ?? "http://localhost:3000";

/** Builds `alternates.languages` for a given locale-agnostic path, e.g. "/login". */
export function buildLanguageAlternates(path: string): Record<string, string> {
  return Object.fromEntries(
    locales.map((locale) => [locale, `${SITE_URL}/${locale}${path}`]),
  );
}

export function canonicalFor(locale: AppLocale, path: string): string {
  return `${SITE_URL}/${locale}${path}`;
}
```

This is the same "one shared module every feature imports" shape as
`lib/api/base-client.ts`'s `apiClient` — don't reimplement alternate-URL
building per page.

### 3.3 Give every public page real, unique metadata

Only the landing page has `generateMetadata` today. Add it to
`app/[locale]/(auth)/login/page.tsx` and `.../register/page.tsx`, following
the exact pattern already in `app/[locale]/(auth)/page.tsx:15-37` (pull
strings from `getTranslation(locale, "common")` or a page-specific
namespace, return `{ title, description }`), and add `alternates.canonical`
+ `alternates.languages` using the Section 3.2 helper:

```ts
export async function generateMetadata({
  params,
}: PageProps<"/[locale]/login">): Promise<Metadata> {
  const { locale } = await params;
  if (!isAppLocale(locale)) return {};

  const { t } = await getTranslation(locale, "auth");
  return {
    title: t("login.metaTitle"),
    description: t("login.metaDescription"),
    alternates: {
      canonical: canonicalFor(locale, "/login"),
      languages: buildLanguageAlternates("/login"),
    },
  };
}
```

Add the new `metaTitle`/`metaDescription` keys to both
`messages/en/auth.json` and `messages/id/auth.json` — same requirement
AGENTS.md's "How to Implement a New Feature" step 5 already calls out for
any new translation key.

While you're in the landing page, also add `openGraph.locale`,
`openGraph.url` (via `canonicalFor`), and a real `openGraph.images` entry —
today it's `title`/`description`/`type` only (`app/[locale]/(auth)/page.tsx:31-35`),
which produces a link preview with no image on every platform that
requires one (iMessage, Slack, WhatsApp).

### 3.4 `noindex` the protected and splash routes

Nothing today tells a crawler these are not results-worthy pages — they're
only unreachable because `proxy.ts:39-46` bounces an unauthenticated
request to `/login`. That's not the same guarantee: an authenticated
crawler session, a leaked direct link, or a search engine that already
indexed the URL before the redirect existed would still surface it.

Two call sites, since there's no shared `(splash)/layout.tsx`:

```ts
// app/[locale]/(protected)/layout.tsx — add alongside the existing default export
export const metadata: Metadata = {
  robots: { index: false, follow: false },
};
```

```ts
// app/[locale]/(splash)/auth-success/page.tsx and .../logout/page.tsx
export const metadata: Metadata = {
  robots: { index: false, follow: false },
};
```

Metadata objects merge shallowly per segment and a child's own `robots`
field fully replaces a parent's (see the "Overwriting fields" behavior in
Next's `generateMetadata` reference) — so setting this once on
`(protected)/layout.tsx` covers `/dashboard` and `/account/[id]` as long as
neither page later adds its own `robots` block that doesn't repeat
`index: false`. Worth a comment at the layout's `metadata` export so a
future page doesn't accidentally undo it.

### 3.5 Add `app/robots.ts` and `app/sitemap.ts`

Both are file-convention Route Handlers — see
[`robots.txt` reference](../node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/01-metadata/robots.md)
and [`sitemap.xml` reference](../node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/01-metadata/sitemap.md)
in this repo's own installed Next.js docs.

```ts
// app/robots.ts
import type { MetadataRoute } from "next";

const SITE_URL = process.env.NEXT_PUBLIC_SITE_URL ?? "http://localhost:3000";

export default function robots(): MetadataRoute.Robots {
  return {
    rules: {
      userAgent: "*",
      allow: "/",
      disallow: ["/*/dashboard", "/*/account", "/*/auth-success", "/*/logout"],
    },
    sitemap: `${SITE_URL}/sitemap.xml`,
  };
}
```

```ts
// app/sitemap.ts
import type { MetadataRoute } from "next";
import { locales } from "@/i18n/settings";
import { canonicalFor, buildLanguageAlternates } from "@/lib/seo/metadata";

const PUBLIC_PATHS = ["/", "/login", "/register"];

export default function sitemap(): MetadataRoute.Sitemap {
  return locales.flatMap((locale) =>
    PUBLIC_PATHS.map((path) => ({
      url: canonicalFor(locale, path === "/" ? "" : path),
      alternates: { languages: buildLanguageAlternates(path) },
    })),
  );
}
```

Only list the three public, static paths — `/dashboard` and
`/account/[id]` are session-gated and dynamic and have no business in a
sitemap meant to drive organic discovery.

### 3.6 Structured data (JSON-LD)

Not covered by the Metadata API at all — Next's own metadata reference
lists `<script type="application/ld+json">` under "Unsupported Metadata,"
to be rendered directly in the page. Add a minimal `Organization`/`WebSite`
block to the landing page:

```tsx
// app/[locale]/(auth)/page.tsx, inside the returned JSX
<script
  type="application/ld+json"
  dangerouslySetInnerHTML={{
    __html: JSON.stringify({
      "@context": "https://schema.org",
      "@type": "WebSite",
      name: "Simple Bank",
      url: canonicalFor(locale, ""),
    }),
  }}
/>
```

Nothing else in the app (dashboard, account pages) is public-facing content
search engines should structure — skip JSON-LD there.

### 3.7 `next/image` — not urgent today

No `<img>` or `next/image` usage exists anywhere in page content today; the
only images are static PWA icons in `public/` wired through
`app/manifest.ts`. There's nothing to migrate right now, but the first time
a page renders a real content image (a logo in the landing hero, a
receipt/avatar), use `next/image` from the start — it ships width/height
and lazy-loading by default, which avoids the layout-shift and slow-LCP
penalties that hurt both Core Web Vitals and ranking. Revisit
`next.config.ts`'s `images` option (remote patterns, formats) only once
there's an actual image to configure.

## 4. Verification

Same three-command gate as everything else in this app (AGENTS.md's "How to
Run and Verify Changes") — `yarn lint && yarn tsc --noEmit && yarn build` —
plus manual checks specific to SEO changes, since none of this is covered
by an automated test (this app has none, per AGENTS.md's "How to Write
Tests"):

- `curl localhost:3000/robots.txt` and `/sitemap.xml` after adding them —
  confirm the disallow list and locale URLs look right.
- View-source (not devtools, which shows the hydrated DOM) on `/en`,
  `/en/login`, `/id/login` — confirm unique `<title>`, `<meta
  description>`, and `<link rel="alternate" hreflang="...">` tags per
  locale.
- Confirm `/en/dashboard` (while logged out, or by temporarily hitting it
  with a valid session cookie) renders `<meta name="robots"
  content="noindex, nofollow">`.
- Run a Lighthouse SEO audit (Chrome DevTools) on the landing page in both
  locales — flags missing alt text, viewport issues, and crawlability
  problems this doc doesn't otherwise catch.

## 5. Priority

Roughly in order of effort-to-impact, if tackled incrementally rather than
all at once:

1. Root metadata + `metadataBase` (3.1) — one file, unblocks everything else.
2. `app/robots.ts` + `app/sitemap.ts` (3.5) — highest impact for the lowest
   effort; without a sitemap, nothing beyond the crawled homepage gets
   discovered at all.
3. `noindex` on protected/splash routes (3.4) — closes an actual (if
   low-severity) information-leak surface, not just a ranking nicety.
4. Per-page metadata + hreflang for login/register (3.3 + 3.2).
5. JSON-LD (3.6) — nice-to-have, landing page only.
6. `next/image` (3.7) — defer until there's an actual image to migrate.
